## A. Что осталось от блокеров после решений

### A-1. Блок «Для бухгалтерії» не заполнится сам 🟡 — актуально

Решение D-7 сократило блок до пяти полей, но требования, которое заставит их заполнить, по-прежнему нет: переходы между статусами свободные (FR-2.9), обязательных полей нет. При этом все пять — **тарифообразующие**, то есть без них менеджер не назовёт цену и данные всё равно всплывут в разговоре.

**Решение:** при переходе в `stage = WON` — неблокирующий чек-лист незаполненных полей с кнопками «Заповнити зараз» / «Пізніше». Плюс строка на дашборде `ADMIN`: «Договори без даних для тарифу (N)». ~2 часа работы вместо полудня — блок стал короче.

### A-2. Контакт без задачи не оставляет следа 🟡 — актуально

«История контактов» — ядро MVP, но фиксируется только через закрытие задачи с результатом (FR-3.5). Менеджер позвонил из машины без задачи → следа нет, а виджет «ліди без активності 7+ днів» (FR-5.2) покажет ложную тревогу.

**Решение:** кнопка **«Зафіксувати контакт»** в drawer и в ПКМ — одно действие, поле результата, создаёт уже закрытую задачу типа `ДЗВІНОК` текущей датой. ~2 часа, закрывает главный источник грязных данных в воронке.

### A-3. Роль `MANAGER` — **снято решением D-4**

Раз любой может забрать любого клиента, а бухгалтер видит всё на чтение, разница между «менеджером» и «співробітником» исчезает. `ADMIN` + `USER` достаточно, новая роль не нужна. В FR-0 надо переписать описание `USER`: не «бухгалтер», а «співробітник».

### A-4. Передача в обслуживание — **снято решением D-1**
### A-5. Импорт ломает аналитику — **снято решением D-3**

## C. Отсутствующие требования

### C-1. Конкурентное редактирование 🟡
Inline-редактирование полей + несколько менеджеров + drawer, который не закрывается. Двое правят тариф одновременно — побеждает последний, второй не узнает. После D-4 (любой правит любого клиента) вероятность выросла.

**Решение:** отдавать `updatedAt` в объекте, слать его в `PATCH`, при расхождении — 409 и тост «Дані змінив інший користувач. Оновити?». Полдня.

### C-2. Утренний дайджест не специфицирован 🟡
Фигурирует в FR-4.5 и в 05-й части, но состав, получатели и поведение в выходные не описаны (05 говорит «выходные копятся», при этом дайджест «отправляется в 08:00»).

**Решение:** 08:00 `Europe/Kyiv`, только будни, только если есть что показать. Состав: просроченные (N), на сегодня (N), нераспределённые лиды (N), ліди без активності 7+ (N) + ссылка. Накопленное за выходные уходит в понедельник.

### C-3. Нет реакции на «лид без активности» 🟡
FR-5.2 показывает виджет, но задача системы — **проконтролировать** работу с новыми клиентами. Виджет контролирует только того, кто на него смотрит.

**Решение:** ежедневная джоба → **одно сводное** уведомление ответственному («3 ліди без активності 7+ днів») + сводка `ADMIN` по всем менеджерам. Не по каждому лиду отдельно — иначе уведомления перестанут читать (принцип уже зафиксирован в NFR-33.4).

### C-4. Статус по умолчанию для новых лидов захардкожен 🟢
FR-W5 и форма создания ставят статус `NEW`, но статусы — редактируемый справочник (FR-2.6). Админ переименует или архивирует `NEW` — создание лида упадёт.

**Решение:** флаг `isDefaultForNew` в `ClientStatus`, ровно одна строка с ним (частичный unique-индекс). Архивировать статус с этим флагом нельзя.

### C-5. Удаление персональных данных по запросу субъекта 🟡
NFR-21 ссылается на ЗУ «Про захист персональних даних» и GDPR, но есть только мягкое удаление на 30 дней и ретеншен аудита.

**Решение:** в v1.1 — действие `ADMIN` «Знеособити клієнта» (затирает ПІБ/телефон/email/РНОКПП/адрес, сохраняет историю статусов и агрегаты). В MVP — только упомянуть в «Порядку обробки», чтобы не обещать лишнего.

### C-6. Ретеншен `WebLead` 🟢
Уведомления — 90 дней, аудит — 12 месяцев, сырой payload заявки (а там ПД) — бессрочно.

**Решение:** `WebLead.rawPayload` очищается через 90 дней после `processedAt`, строка остаётся.

### C-7. «КП без відповіді 5+ днів» 🟢
Виджет нарисован на дашборде в `06`, требования под него нет.

**Решение:** добавить в FR-5.2: клиенты в статусе `PROPOSAL_SENT` дольше N дней (N — в `app_settings`, дефолт 5).

### C-8. Повторная заявка с сайта не создаёт задачу 🟢
FR-W6 пишет событие в ленту и уведомляет ответственного. Если открытой задачи-звонка нет, повторное обращение может остаться без действия.

**Решение:** при повторной заявке, если открытой задачи типа `ДЗВІНОК` по клиенту нет, создать её на сегодня.

### C-9. Средний срок прохождения воронки не определён 🟢
FR-5.1 упоминает метрику, FR-2.9 разрешает свободные переходы туда-обратно.

**Решение:** считать от **первого** входа в `stage = LEAD` до **первого** входа в `stage = WON`; вернувшиеся назад не пересчитываются.

### C-10. Уведомление о новой заявке с сайта 🟡
FR-W5 создаёт лида без ответственного и задачу без исполнителя. Уведомлять некого — событий «назначена задача» не происходит. Лид виден только на дашборде `ADMIN` и бейджем в сайдбаре.

**Решение:** новая заявка → уведомление **всем активным пользователям** (in-app + Telegram, приоритет `NORMAL`). Заявок единицы в неделю, спама не будет, а лид попадает в работу в минуты, а не на следующий день.

### Не трогать, хотя выглядит дорого

- **Приём заявок с сайта** (FR-W1–W9) — после отмены импорта это **единственный** способ наполнить систему без ручного ввода и единственный источник честной конверсии по каналам.
- **Реестр действий + ПКМ** (раздел 8) — прямо заявленный приоритет заказчика, и он же удерживает сотрудников в системе.
- **Inline-редактирование полей** — то, что отличает быструю CRM от медленной.
- **Обязательный результат звонка** (FR-3.5) — без него нет истории контактов, ради которой всё затевалось.
- **Бэкапы, запись в аудит, права** — цена ошибки не зависит от размера системы.
