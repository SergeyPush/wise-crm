# Нефункциональные требования

## Масштаб (проектные цифры — от них считаем всё остальное)

| Параметр              | Значение на 2 года                                                             |
| --------------------- | ------------------------------------------------------------------------------ |
| Пользователей всего   | 10                                                                             |
| Одновременно активных | 5–7                                                                            |
| Клиентов              | 2 000 (накопительно за 2 года; система стартует пустой — импорта нет, FR-2.15) |
| Задач                 | 100 000                                                                        |
| Файлов                | 20 ГБ                                                                          |
| Пиковый RPS           | ~3                                                                             |

Вывод: это **очень маленькая система**. Никаких микросервисов, k8s, Kafka, Redis, шардирования, реплик. Один процесс NestJS и один Postgres тянут это с 50-кратным запасом; узкое место — не нагрузка, а сложность, которую можно себе сделать самому.

**Инфраструктурный бюджет MVP — два новых контейнера: `api` и `postgres`.** Nginx уже стоит под сайт. Всё остальное в этих документах либо внешнее и бесплатное, не занимающее ресурсов сервера (UptimeRobot/Healthchecks, Cloudflare, Telegram), либо не сервис вообще (бэкап — `pg_dump` и `tar` по крону).

Правило при любом предложении «давайте поставим X»: **новый контейнер добавляется только когда без него функция физически невозможна**, а не когда с ним удобнее. По этому правилу из MVP уже исключены Redis/BullMQ (крон-воркер в том же процессе), GlitchTip (NFR-32) и ClamAV (FR-F13 — он один требует больше памяти, чем всё приложение, и на текущем тарифе физически не помещается).

Практические следствия для 10 пользователей:

- WebSocket/SSE не нужны — polling раз в минуту дешевле и надёжнее;
- очереди не нужны — крон-воркер в том же процессе;
- кэш не нужен — Postgres с индексами отвечает за единицы миллисекунд;
- виртуализация таблиц не нужна — серверной пагинации по 25–100 строк достаточно;
- аналитические запросы дашборда можно считать на лету, без агрегирующих таблиц.

Единственное, что от малого масштаба **не** упрощается — бэкапы, права доступа и аудит. Их делаем полностью: цена потери данных не зависит от числа пользователей.

## Производительность

- NFR-1 API p95 < 200 мс, p99 < 500 мс (без учёта сети). Измеряется по полю `duration` в pino-логах (NFR-31) — иначе требование непроверяемо.
- NFR-2 Первая загрузка SPA: LCP < 1.5 с на 4G, JS-бандл gzip < 300 КБ (initial chunk), route-based code splitting. В initial chunk **запрещено** попадать `@mantine/charts`, `@mantine/tiptap`, `@mantine/dropzone`, `dnd-kit` (канбан) и экранам админки — только `lazy()`. С Mantine (~100 КБ gzip) + React + Router + Query бюджет выполним только при этом условии; проверка размера бандла — в CI.
- NFR-3 Переход между экранами < 100 мс (данные из кэша TanStack Query + prefetch по hover).
- NFR-4 Список клиентов: только серверная пагинация, `limit ≤ 100`. Запрещено `SELECT *` без `LIMIT`. Канбан (FR-2.12) — не исключение: 50 карточек на колонку + «показати ще».
- NFR-5 Обязательные индексы: `clients(status_id)`, `client_assignees(user_id)` (запрос «мої клієнти» — самый частый в системе), `clients(edrpou)`, `clients(rnokpp)`, `clients(deleted_at)`, `clients(last_activity_at)`, GIN trigram на `clients(display_name)`, `client_contacts(phone_normalized)`, `client_contacts(email)`, `tasks(assignee_id, status, due_at)`, `tasks(client_id)`, `activity_events(client_id, created_at DESC)`, `audit_log(created_at)`. Индексы по `group_id` и `kep_expires_at` убраны вместе с полями.
- NFR-5.1 Телефон хранится дважды: как ввёл пользователь и нормализованным `+380XXXXXXXXX` в `phone_normalized`. Без нормализации поиск по `0671234567` не находит `+38 (067) 123-45-67` (FR-2.10) и не срабатывает проверка дублей (FR-2.2).
- NFR-6 N+1 запрещён: списки — один запрос с join/`include`, счётчики — агрегатом. Логировать в dev запросы > 50 мс.

## Надёжность и доступность

- NFR-7 Доступность 99% в рабочие часы (9:00–19:00, `Europe/Kyiv`). Ночной деплой с даунтаймом до 2 мин допустим.
- NFR-8 **Бэкап — локальный, без внешнего хранилища** (решение от 26.08.2026). `pg_dump -Fc` ежедневно в 03:00 плюс снапшот тома `uploads` в `/var/backups/wise-crm` (`chmod 700`, владелец `deploy` — там нешифрованные ПД и `.env`). Хранение: **не более трёх суточных копий**. WAL на этом масштабе не нужен.
  **Окно восстановления — трое суток**, и это принятое ограничение: порча данных, замеченная на четвёртый день, из локального бэкапа не откатывается. Для воронки продаж приемлемо — испорченный статус или удалённый лид замечают в тот же день.
  **Единственная копия за пределами сервера — снапшоты VPS у хостера**, поэтому они обязательны, а не желательны. Потеря доступа к аккаунту Hostinger означает потерю данных: это принятый риск, зафиксированный в `04-deployment.md` и `07-open-questions.md`. Требование «копия вне ЦОД, ЄС-регион» снято вместе с offsite-копией; ПД теперь не покидают сервер вообще, что упрощает NFR-21, но не заменяет резервирование.
- NFR-9 RPO 24 ч. При аварии под конец дня теряется рабочий день (внесённые клиенты, комментарии, поставленные задачи), и это принято. Если позже покажется дорого — снижается до 6 ч добавлением трёх строк в crontab, без изменений в приложении.
- NFR-9.1 **RTO: 2 часа в рабочие часы (9:00–19:00 `Europe/Kyiv`, пн–пт), вне их — до начала следующего рабочего дня.** Формулировка изменена 26.08.2026 после ответа «никто не дежурит». Единого RTO 2 ч быть не может: восстановление выполняет человек, а дежурства нет — авария в субботу в 23:00 будет замечена в понедельник утром независимо от того, что написано в требованиях. Записываем достижимую цифру, а не желаемую.
  Что реально снижает риск вместо дежурства: `restart: unless-stopped` + healthcheck (NFR-11) сами поднимают упавший контейнер — типовой отказ чинится без человека; снапшоты VPS (NFR-8) делают ночной простой потерей времени, а не данных; учебное восстановление раз в квартал (NFR-9.2) держит процедуру в рабочем состоянии.
- NFR-9.2 Раз в квартал — учебное восстановление по runbook, с секундомером, по обоим сценариям: точечный откат из локального дампа и подъём машины из снапшота хостера (`04-deployment.md`). Иначе бэкапов у вас нет, есть только файлы.
- NFR-10 Бэкап `uploads/` — **снапшотами на жёстких ссылках** (`rsync --link-dest`) через временный контейнер (том принадлежит `root`), а не архивом. Три «полных» снапшота стоят примерно один объём плюс дельты; три архива подряд заняли бы треть 50-гигабайтного диска (NFR-41) ради считанных мегабайт изменений. Проверка, что жёсткие ссылки реально работают, — пункт чек-листа прода.
- NFR-11 Healthcheck `/api/v1/health` (liveness) и `/api/v1/health/ready` (проверка БД) — единственные пути без аутентификации и без rate limit. Один и тот же путь в `docker healthcheck`, во внешнем мониторинге (NFR-33) и в runbook. Рестарт-политика `unless-stopped`.
- NFR-12 Graceful shutdown: дождаться текущих запросов (Nest `enableShutdownHooks`), 10 с таймаут.

## Безопасность

- NFR-13 Только HTTPS, HSTS, авто-сертификат Let's Encrypt. HTTP → 301.
- NFR-14 Пароли: Argon2id (`m=19MiB, t=2, p=1`), минимум 10 символов, проверка по списку топ-10k утёкших. Список — **локальный файл в репозитории**; наружу (HIBP и подобные) пароли и их хеши не отправляем.
- NFR-15 Токены в `httpOnly` cookie (не в localStorage — защита от XSS-кражи). CSRF: `SameSite=Lax` + double-submit токен на мутациях.
- NFR-16 Rate limit. Основное ограничение логина — **по email** (единое правило описано в FR-1.5). По IP — 20 попыток/мин, а не 5: десять сотрудников сидят за одним офисным NAT, и жёсткий лимит блокирует весь офис из-за чужих опечаток. Остальное: 100 req/мин на пользователя, 20 req/с общий (на реверс-прокси). Healthcheck (NFR-11) — вне лимитов.
- NFR-17 Авторизация проверяется **на сервере в каждом эндпоинте** (guard + проверка владения объектом). Скрытие кнопок во фронте — UX, не защита.
- NFR-18 Валидация всего входа: `class-validator` + `whitelist: true, forbidNonWhitelisted: true`. Никаких сырых DTO в ORM.
- NFR-19 SQL — только через ORM/параметризованные запросы. Загрузка файлов: проверка magic bytes, а не расширения; отдача с `Content-Disposition: attachment` и `X-Content-Type-Options: nosniff`.
- NFR-20 Секреты — в `.env` на сервере (chmod 600), никогда в git. В репозитории `.env.example`.
- NFR-21 Персональные данные (ЗУ «Про захист персональних даних», ст. 24; при клиентах из ЕС — GDPR): данные клиентов и контактов хранятся на сервере в Украине или ЕС; в логах не пишем телефоны/email/РНОКПП (маскирование в логгере); внутренний документ «Порядок обробки персональних даних», доступ по ролям, журнал доступа = аудит-лог (NFR-22).
- NFR-21.1 Все внешние сервисы, которым уходят ПД, — только с ЄС-регионом или под договором обработки: трекер ошибок, если он когда-нибудь появится (NFR-32.4 — только EU-регион, и с вырезанием тела запроса: там ЄДРПОУ и телефоны, а для разбора хватает `requestId`). **Telegram** (FR-4.2) — тоже внешний обработчик: шаблоны уведомлений не содержат ПД клиентов (без телефонов, email, РНОКПП), только тип события, `displayName` и ссылку на объект в CRM. Это ограничение — часть спецификации шаблонов, а не пожелание.
- NFR-22 Аудит-лог неизменяем: приложение делает только INSERT, UPDATE/DELETE-эндпоинтов нет. Единственное исключение — джоба ретеншена (FR-7.1, 12 мес), удаляющая строки батчем строго по возрасту; факт запуска и число удалённых строк логируются.
- NFR-23 `npm audit` / Dependabot в CI; обновление зависимостей раз в месяц.
- NFR-42 **CSP обязателен**: `default-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'self'`, без inline-скриптов. Разделение origin (вариант Г в `04-deployment.md`) и CSP решают одну задачу вдвоём; без CSP первая же XSS в зависимости фронта отдаёт всю базу.
- NFR-43 **2FA (TOTP) в MVP не делается** (решение от 26.08.2026, пересмотр; было — обязательна для `ADMIN`). Трение при каждом входе и точка отказа (утерянный телефон, отдельный CLI-путь восстановления) не окупались на масштабе в одного-двух админов. Защита логина — пароль (Argon2id, NFR-14) и лимит попыток (FR-1.5). Кандидат на возврат в v1.1, см. `01-functional-requirements.md`, раздел 9.
- NFR-45 **Таймзона.** В контейнере явно выставляется `TZ=Europe/Kyiv`, но приложение на это **не полагается**: все календарные вычисления («сьогодні», «прострочено», дайджест в 08:00, джобы) идут через `date-fns-tz` с явной зоной, а в БД всё хранится в UTC `timestamptz` (FR-3.1.1). Две меры вместо одной, потому что каждая по отдельности уже ломалась: голый `TZ` теряется при смене базового образа, а голый `date-fns-tz` не спасает крон-выражения `@nestjs/schedule`. Проверка — пункт в чек-листе прода.
- NFR-46 **Оптимистичная блокировка при редактировании.** Мутации карточки клиента и задачи принимают `updatedAt` объекта; при расхождении — `409` и тост «Дані змінив інший користувач. Оновити?».
  Нужна именно здесь: inline-редактирование полей (`06-ui-layout.md`) плюс правило «любой правит любого клиента» (FR-0.3) означают, что двое одновременно на одной карточке — обычное дело, а «побеждает последний» теряет чужую правку молча.
- NFR-44 **Алерт на аномальную выгрузку — v1.1** (решение от 26.08.2026): > 50 скачиваний файлов одним пользователем за час → уведомление админу. На старте риск «увели базу» закрывает FR-E6 (уведомление о полной выгрузке); поштучное скачивание документов как обходной путь остаётся открытым и это принятое ограничение MVP.

> Номера NFR — уникальные идентификаторы, а не порядок следования; новые добавляются в конец нумерации.

## Удобство (для бухгалтерии это критичнее производительности)

- NFR-24 Создание клиента — одна форма, ≤ 6 обязательных полей, остальное сворачивается в «дополнительно».
- NFR-25 Любое действие ≤ 3 кликов от главной. Глобальный поиск по `Ctrl/Cmd+K` (клиенты + задачи).
- NFR-26 Нет модалок поверх модалок. Формы сохраняются по `Cmd+Enter`. Ошибки — под полем, человеческим языком **українською** (NFR-29).
- NFR-27 Оптимистичные апдейты для смены статуса/закрытия задачи (мгновенный отклик, откат при ошибке).
- NFR-28 Адаптив: полноценно — от 1280px; телефон — read-only просмотр карточки клиента и списка «мої задачі» (сотрудники работают с десктопа, тратить недели на мобильную вёрстку не нужно).
  **Исключение — два действия по задаче: «Виконано» (с полем результата) и «Перенести термін»** (решение от 26.08.2026). Уведомления в Telegram (FR-4.2) ведут именно на задачу, и полностью read-only телефон означает, что менеджер получает напоминание в дороге и не может ничего с ним сделать. API уже есть, вёрстка — две кнопки.
  Тач-жесты из FR-8.7 (долгое нажатие → контекстное меню) относятся к планшетам и тач-десктопам; на телефоне остального интерфейса действий нет.
- NFR-29 Интерфейс полностью на **украинском** (ЗУ «Про забезпечення функціонування української мови», ст. 27 — интерфейс ПО, используемого в обслуживании клиентов, должен быть украиноязычным). Даты `дд.мм.рррр`, деньги `1 234,56 ₴`, локаль `uk-UA`, таймзона `Europe/Kyiv` (в БД всё в UTC `timestamptz`). i18n-слой (`i18next`) закладываем сразу, вторым языком при желании — русский.
- NFR-30 Пустые состояния везде объясняют, что делать («Клієнтів ще немає. Додайте першого або дочекайтеся заявки з сайту»). Формулировок про импорт из Excel быть не должно — импорта в системе нет (FR-2.15).

## Наблюдаемость

- NFR-31 Структурированные JSON-логи (`pino`), `requestId` сквозной, уровень из env. Ротация через `docker` json-file driver (max 50 МБ × 5).
- NFR-31.1 **Что пишется в лог на каждый запрос:** метод, путь, статус, `duration`, `requestId`, `userId` (не email), IP. **Тело запроса и ответа не логируется никогда** — там ЄДРПОУ, телефоны и суммы договоров (NFR-21). Ошибка 5xx пишется со стеком; 4xx — одной строкой без стека, иначе лог забивается опечатками пользователей.
- NFR-31.2 **`requestId` возвращается клиенту** в теле ошибки и показывается в интерфейсе: «Сталася помилка. Код: `a3f9c1`». Без этого жалоба «у меня всё сломалось вчера днём» не связывается с логом никак, и разбор превращается в гадание. Это самая дешёвая диагностическая функция из существующих — одно поле в ответе и одна строка в UI.
- NFR-31.3 **Логируются события безопасности**, которых нет в аудите (он покрывает только мутации): неудачный вход, блокировка по FR-1.5, отказ авторизации (403), срабатывание rate limit, запрос к чужому объекту. Отдельный уровень `warn` и тег `security` — чтобы их можно было отфильтровать одной командой.
- NFR-31.4 **Фоновые задачи логируют результат каждого прогона** — outbox уведомлений, обработка веб-заявок, экспорт, ретеншен, бэкап. Падение джобы **отправляет алерт** (NFR-33.1), а не остаётся строкой в логе: молча вставший воркер уведомлений выглядит как «нам просто никто не пишет», и обнаруживается через неделю по вопросу «а почему не приходят напоминания».
- NFR-31.5 Логи Docker живут 3–7 дней (50 МБ × 5). Этого хватает на «разобраться сегодня», но не на «вспомнить, что было в прошлом месяце» — и это принятое ограничение MVP (NFR-32).

### Ошибки: без внешних сервисов в MVP

- NFR-32 **Sentry и GlitchTip в MVP не ставим** (решение от 26.08.2026). GlitchTip на своём VPS — это три дополнительных контейнера и ~1 ГБ RAM ради десяти пользователей; Sentry SaaS не грузит сервер, но добавляет внешний аккаунт, ключи и поток персональных данных наружу. Ни то ни другое не оправдано, пока систему используют несколько человек.
  Вместо этого — **два механизма, оба на уже существующей инфраструктуре**:
  1. `pino` в stdout контейнера (NFR-31) — полный контекст для разбора;
  2. **алерт в Telegram при ошибке 5xx** через того же бота, что уже настроен для уведомлений (FR-4.2). Сообщение: тип ошибки, `requestId`, путь, время. Без стека и без данных — стек смотрится в логе по `requestId`.
- NFR-32.1 **Дедупликация алертов обязательна**: одинаковая сигнатура ошибки (хеш от типа + места) шлётся не чаще раза в час, в сообщении — счётчик («×17 за годину»). Без этого одна зацикленная ошибка превращает рабочий чат в мусор, и алерты перестают читать все и навсегда.
- NFR-32.2 **Ошибки фронтенда** серверных логов не достигают вообще — белый экран у менеджера не оставляет следов нигде. Поэтому: React error boundary и `window.onerror` шлют событие на свой же эндпоинт `POST /api/v1/client-errors` (сообщение, компонент, URL, `requestId` последнего запроса), он логируется наравне с серверными. Свой эндпоинт вместо внешнего сервиса: час работы, ноль новых зависимостей, данные не покидают сервер. Rate limit 10/мин на пользователя, чтобы зацикленный компонент не залил диск.
- NFR-32.3 Необработанные исключения и `unhandledRejection` логируются и шлют алерт **до** завершения процесса; graceful shutdown (NFR-12) не должен глотать причину падения.
- NFR-32.4 **Когда подключать полноценный трекер ошибок:** если ошибок станет столько, что Telegram-алерты перестанут читаться, или появится потребность в группировке, трендах и source maps. Тогда — **Sentry SaaS с EU-регионом**, а не self-hosted: интеграция это SDK и один DSN в env, полдня работы. Код к этому готов — логирование уже централизовано в одном месте, менять придётся только транспорт.
- NFR-33 Uptime-мониторинг снаружи (UptimeRobot/Healthchecks.io) на `/api/v1/health` + алерт в Telegram. Отдельный чек, что бэкап отработал (dead man's switch).
- NFR-33.1 **Алерты мониторинга отправляются в момент события, круглосуточно, без задержек, тихих часов и дедупликации.** Тихие часы 20:00–08:00 (FR-4.4) — правило для продуктовых уведомлений о задачах и клиентах; к алертам инфраструктуры оно **не применяется**. Это разные подсистемы: продуктовые уведомления идут через outbox с ретраями, алерты — напрямую из внешнего мониторинга в Telegram.
- NFR-33.2 Алерты уходят в **групповой чат**, а не одному человеку: дежурства нет (NFR-9.1), и единственный получатель, у которого разрядился телефон, = никто не узнал. В чате — все `ADMIN` и разработчик.
- NFR-33.3 Тексты алертов пишутся так, чтобы получатель понял без расследования: что упало, с какого момента, что делать первым шагом, ссылка на runbook. «CRM DOWN» в три часа ночи бесполезен; «CRM не відповідає з 03:12. Контейнер перезапускається автоматично. Якщо через 10 хв не піднялося — runbook, крок 3» — работает.
- NFR-33.4 Флап-контроль: алерт «упало» отправляется после двух подряд неудачных проверок (интервал 60 с), «поднялось» — сразу. Иначе после сетевой моргания чат наполняется шумом и на него перестают смотреть — что при отсутствии дежурства особенно опасно.
- NFR-34 Метрики (Prometheus/Grafana) — не нужны на старте: проверка NFR-1 делается разбором `duration` из pino-логов раз в неделю. Если понадобится больше: `prom-client` + Grafana Cloud free.

## Поддерживаемость

- NFR-35 TypeScript strict на фронте и бэке. Общие типы API — один источник правды (см. архитектуру).
- NFR-36 Миграции БД версионируются в репозитории, применяются автоматически при старте контейнера. Откат — только через новую миграцию, поэтому обязательны два правила: (1) CI делает `pg_dump` **до** деплоя, (2) политика expand/contract — колонка не удаляется в том же релизе, где перестала использоваться; удаление уходит в следующий релиз. Иначе неудачная миграция = простой без пути назад.
- NFR-37 **Три уровня тестов, каждый со своей задачей** (детальный состав и конкретные цели — `09-implementation-plan.md`, раздел 5):
  - **юнит** (Vitest) — бизнес-правила: валидация ЄДРПОУ/РНОКПП/IBAN, нормализация телефона (NFR-5.1), календарь `Europe/Kyiv` (FR-3.1.1), матрица прав, маппинг веб-формы (FR-W4);
  - **API** (Vitest + `supertest` + настоящий Postgres, не моки) — права, контракт, валидация, транзакционность и побочные эффекты: запись в ленту и аудит, `409` при конкурентной правке (NFR-46), приём заявок с сайта (FR-W1–W6);
  - **UI** (Playwright, headless Chromium) — **восемь сценариев, и это потолок, а не «пока хватит»**: логин, заведение лида, заявка → «Взяти в роботу», ПКМ с оптимистичным откатом, обязательный результат звонка, чек-лист перед закрытием сделки, F5 на глубоком URL, права глазами `USER`.
    Цель прежняя и не меняется: **не проценты покрытия, а «CI ловит поломку прав доступа и бизнес-правил»**. Метрика покрытия при такой цели — способ написать много тестов на геттеры. Нагрузочных тестов нет: 3 RPS и 10 пользователей делают их измерением качества стенда, а не системы.
- NFR-37.1 Тесты пишутся **вместе с функцией**, а не отдельным этапом в конце: на проекте одного разработчика «сначала сделаем, потом покроем» означает «не покроем». Тестовая инфраструктура ставится на неделе 1, до бизнес-логики. Цена — ~1,5 недели из общей оценки, и она заложена в срок, а не выдавливается из него.
- NFR-38 Гейты CI: на pull request — линт, typecheck, юнит и API-тесты; на merge в `main` — дополнительно Playwright; деплой только с зелёного `main`. Прогон на PR укладывается в пять минут; если API-тесты вырастут за этот бюджет, они шардируются, а не сокращаются.
- NFR-39 Один разработчик должен уметь поднять проект локально одной командой `docker compose up`.

## Ограничения

- NFR-40 Браузеры: Chrome/Edge/Firefox/Safari последние 2 версии. IE11 — нет.
- NFR-41 **Ресурсы: 1 vCPU / 4 ГБ RAM / 50 ГБ диска** — тот же VPS Hostinger, что и сайт (подтверждено 26.08.2026). Это меньше изначально заложенных 2 vCPU / 80 ГБ, и MVP в них помещается только благодаря сокращениям: без импорта 2 000 клиентов проектный объём — ~22 ГБ из 50 (расчёт в `04-deployment.md`).
  Что из этого следует как требование, а не пожелание:
  - лимиты памяти контейнеров в compose (`postgres` 1,5 ГБ, `api` 768 МБ), `shared_buffers = 512MB`, `max_connections = 20`, пул Prisma 10 — иначе OOM-killer выберет жертву сам, и ею может оказаться сайт;
  - swap 2 ГБ обязателен;
  - сборка образов только в CI, не на сервере;
  - бэкап под `nice`/`ionice` (ядро одно);
  - **отказ в загрузке файла при заполнении диска > 85 %** с внятным сообщением, алерт при > 80 % (NFR-33);
  - **ClamAV (FR-F13) на этом тарифе невозможен** — ему нужен ~1 ГБ RAM только под сигнатуры. Это не «v1.1», а «после смены тарифа».
    Апгрейд до 2 vCPU / 8 ГБ понадобится, если добавится антивирус, вернётся импорт исторической базы или в системе появится бухгалтерский контур с первичкой.
