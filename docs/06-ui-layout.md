# Интерфейс: компоновка экранов и дизайн-система

## Нужна ли отдельная дизайн-система? Нет

**Mantine — это уже дизайн-система**: токены, сетка, типографика, состояния, доступность, тёмная тема. Строить свою поверх неё для 10 внутренних пользователей — это недели работы с нулевой отдачей: дизайн-системы окупаются, когда несколько команд делают несколько продуктов.

Что действительно нужно — **тонкий слой в один рабочий день**:

1. **Тема** — 20 строк токенов (акцентный цвет с сайта, радиусы, шрифт, плотность).
2. **8 обёрток-паттернов** — чтобы экраны не расползались (список ниже).
3. **Карта экранов и правила компоновки** — то, ради чего этот документ.
4. **Обязательный набор состояний** для каждого экрана (загрузка / пусто / ошибка / нет прав).

Storybook тоже не нужен: хватит страницы `/dev/ui` с примерами всех обёрток, доступной только в dev-сборке.

## Карта экранов

| Путь | Экран | Кто | Главный элемент |
|---|---|---|---|
| `/login` | Вход | все | форма по центру, ничего лишнего |

| `/settings/dictionaries` | Справочники | admin | CRUD-таблицы: джерела, причини відмови, теги (повний) + статуси клієнтів (обмежений — назва/колір/порядок, створення) |
| `/settings/users` | Пользователи | admin | таблица + drawer |
| `/settings/web-leads` | Заявки с сайта | admin | журнал: payload, результат разбора, ошибки (FR-W9) |
| `/profile` | Профиль | все | Telegram-тумблер, пароль |

**Десять экранов.** Из первоначальных тринадцати убраны: `/settings/export` (экспорт стал кнопкой в списках, FR-E1), `/clients/board` (канбан → v1.1, FR-2.12), `/settings/audit` (запись в аудит идёт с первого дня, экран просмотра → v1.1, FR-7.1). Всё, что не влезло — вкладки внутри оставшихся. Если экранов станет двадцать, скорость работы упадёт: сотрудник перестаёт помнить, где что.

Карточка задачи нужна отдельно: у задачи есть комментарии, файлы и результат закрытия, а ссылки из уведомлений (in-app и Telegram) ведут именно на задачу — им нужен адресуемый URL. Открывается тем же `EntityDrawer`, что и клиент.

## Решение №1: таблица + боковой drawer, а не «список → отдельная страница»

Клик по строке открывает **правый drawer** (600 px) с быстрым просмотром: статус, ответственный, контакты, ближайшая задача, последние 5 событий, кнопки действий. `Esc` закрывает, стрелки ↑/↓ листают клиентов **не закрывая drawer**.

Полная карточка (`/clients/:id`) открывается по `Enter`, двойному клику или кнопке «Відкрити повністю».

Почему так: 80 % обращений к клиенту — «глянуть телефон», «в каком статусе», «когда последний раз звонили». Полноценный переход на страницу и обратно теряет позицию в списке, фильтры и прокрутку. Drawer держит контекст.

```
┌──────────────────────────────────────┬──────────────────────────────┐
│  таблица клиентов (продолжает жить)  │  ТОВ «Ромашка»          ✕   │
│  ▸ ТОВ «Ромашка»          ← выбран   │  ● Договір підписано ▾       │
│  ▸ ФОП Петренко І.                   │  Олена П. · +Ірина (помічн.) │
│  ▸ ТОВ «Будмайстер»                  │  ЄП 3 гр. 5% · без ПДВ       │

```

## Экран «Клієнти»

```
Клієнти                                                          [Експорт] [+ Клієнт]
──────────────────────────────────────────────────────────────────────────────────────
[🔍 пошук: назва, ЄДРПОУ, телефон]  [Статус ▾] [Відповідальний ▾] [Оподаткування ▾] [Ще ▾]
⟨Мої активні⟩ ⟨Ліди в роботі⟩ ⟨Нерозподілені ②⟩ ⟨Прострочені⟩
──────────────────────────────────────────────────────────────────────────────────────
☐ │ Назва           │ Статус       │ Відповід. │ Телефон      │ Оподатк. │ Тариф │ Наст. задача    │ ⋮
☐ │ ТОВ «Ромашка»   │ ● Договір    │ Олена     │ +380671234567│ ЄП3 5%   │ 5 000 │ КП · завтра     │ ⋮
☐ │ ФОП Петренко    │ ● Лід        │ Ігор      │ +380502223344│ ЄП2      │   —   │ Дзвінок · прострочено │ ⋮
──────────────────────────────────────────────────────────────────────────────────────
Обрано 2 ▸ [Змінити статус] [Змінити відповідального] [Тег] [Експорт]      ‹ 1 2 3 ›  25 ▾
```

- **Порядок колонок = порядок важности** и он **фиксирован** (FR-2.11.2): назва → статус → ответственный → телефон → налогообложение → тариф → следующая задача. Настройка видимости и порядка колонок — v1.1.
- Четыре чипа над таблицей — не сохранённые представления, а зашитые в код пресеты фильтров (FR-2.11.1). Произвольный фильтр по-прежнему живёт в URL и шарится ссылкой; сохранить свой набор кнопкой пока нельзя.
- Отдельно от чипов — вкладки «Усі / Мої / Ліди в роботі / Нерозподілені (/ Архів для `ADMIN`)»: **«Усі» первая и активна по умолчанию** (рішення користувача 28.08.2026), «Мої» — друга.
- Плотность: высота строки 40 px, шрифт 13 px, залипающая шапка. На 1920×1080 помещается ~20 строк — этого достаточно, чтобы не листать.
- Строка «прострочена задача» подсвечивается левой красной полосой, а не заливкой всей строки (заливка убивает читаемость).
- ПКМ по строке и по нескольким выделенным — раздел 8 в `01-functional-requirements.md`.
- Пагинация серверная, 25/50/100. Бесконечный скролл не делаем: в нём невозможно «вернуться туда, где был».

**Канбана в MVP нет** (FR-2.12): воронка видна виджетом на дашборде и фильтром по статусу, статус меняется из ПКМ и drawer одним действием. Drag-n-drop вернётся в v1.1 — и тогда та же панель фильтров, колонки по статусам, 50 карточек + «показати ще», цвет колонок из справочника статусов.

## Карточка клиента

```
← Клієнти /  ТОВ «Ромашка»                                    [⋮ Дії]  [Відкрити задачі]
┌────────────────────────────────────────────────┬───────────────────────────────────┐
│ [Огляд] [Задачі ④] [Документи ⑦] [Історія] [💬] │  ● Договір підписано        ▾    │
│                                                │  Олена П. (основна) +Ірина  ▾    │
│  РЕКВІЗИТИ                    ДЛЯ ТАРИФУ       │  Тариф: 5 000 ₴/міс              │
│  Повна назва   ТОВ «Ромашка»  Система  ЄП 3 5% │  Договір №14 від 15.01.2026      │
│  ЄДРПОУ        12345678       ПДВ      Ні      │  ─────────────────────────       │
│  Адреса        м. Київ...     Праців.  4       │  Останній контакт: 3 дні тому    │
│  КВЕД          62.01          Док/міс  120     │  ─────────────────────────       │
│                               Дія.City Ні      │  КОНТАКТИ                        │
│                                                │  Іванов І. — директор            │
│  КОМЕРЦІЯ                                      │  📞 +380 67 123-45-67  ⧉ 📱      │
│  Договір №14 від 15.01.2026                    │  ✉ ivanov@romashka.ua  ⧉         │
│  Тариф 5 000 ₴/міс                             │  ─────────────────────────       │
│                                                │  [+ Задача] [Контакт] [+ Док]    │
└────────────────────────────────────────────────┴───────────────────────────────────┘
```

- **Правая колонка залипающая** — статус, ответственные, тариф, договор, последний контакт, контакты и кнопки видны с любой вкладки. Именно это смотрят чаще всего.
- **Ответственные** (FR-2.0): основной показан именем, помощники — аватарами со всплывающей подсказкой. В таблице колонка «Відповід.» показывает основного + «+1». Фильтр по ответственному находит клиента по любому из них.
- **Кнопка «Контакт»** (FR-2.2.1) открывает поле результата и создаёт закрытую задачу-звонок. Она стоит рядом с «+ Задача» намеренно: зафиксировать состоявшийся разговор должно быть не дороже, чем запланировать будущий.
- **Inline-редактирование полей**: клик по значению превращает его в поле ввода, сохранение по `Enter`/blur, отмена по `Esc`. Модалка «Редагувати клієнта» с 25 полями ради изменения одного — главный убийца скорости в самописных CRM. Конфликт двух одновременных правок разрешается по `updatedAt` (NFR-46), а не «побеждает последний».
- **Блок «Для тарифу»** (система оподаткування, ПДВ, працівники, документів на місяць, Дія.City) — **свёрнут по умолчанию** и раскрывается на этапе КП. В форме создания лида его нет: там четыре поля (FR-2.0.4). При переходе в «Договір підписано» незаполненные поля показываются чек-листом (FR-2.0.5).
- Смена статуса и ответственного — прямо в правой колонке из выпадающего списка.
- Вкладка «Документи» — категории слева, файлы справа, drag-n-drop на всю область (см. `05-files-and-notifications.md`).
- Вкладка «Історія» — Mantine `Timeline`: статусы, задачи, файлы, изменения полей, комментарии; фильтр по типу события.

## Экран «Задачі»

**Группировка по срокам вместо плоской таблицы** — бухгалтер думает категориями «что горит», а не «отсортировать по дате»:

```
Задачі       [Всі | Мої | Завершені | Календар]   [Тип ▾] [Виконавець ▾] [Клієнт ▾]   [Повна форма] [+ Задача]
────────────────────────────────────────────────────────────────────────────────────
[ Що зробити? ______________________________________________ ] ⏎ → задача на себе, сьогодні
────────────────────────────────────────────────────────────────────────────────────
⚠ ПРОСТРОЧЕНІ (3)
  ☐ 📞 Подзвонити щодо документів   ТОВ «Ромашка»    вчора    Олена   ⋮
  ☐ 📄 Підготувати КП               ФОП Петренко     3 дні    Ігор    ⋮
СЬОГОДНІ (5)
  ☐ 📑 Договір на підпис            ТОВ «Будмайстер» 15:00    Олена   ⋮
ЦЬОГО ТИЖНЯ (12)   ▸ згорнуто
БЕЗ ТЕРМІНУ (4)    ▸ згорнуто
```

- Порядок вкладок: **«Всі» — перша й активна за замовчуванням** (рішення користувача 28.08.2026), «Мої» — друга. Раніше було навпаки.
- Рядок вводу зверху: `Enter` → задача на себе на сьогодні. Дозаповнити деталі можна потім. Це знімає головний бар'єр — «поставити задачу довше, ніж зробити». Кнопка **«Повна форма»** поруч (зроблено 27.08.2026) — заголовок + клієнт + тип + виконавець + термін за один крок, коли швидкого рядка не досить.
- Чекбокс зліва завершує задачу; для типів `ДЗВІНОК/КП/ДОГОВІР` спочатку питається результат (FR-3.5).
- ПКМ → перенос терміну в один клік (сьогодні / завтра / +3 дні / тиждень).
- Вкладка **«Календар»** (зроблено 27.08.2026, FR-3.4) — місячна сітка Пн–Нд на 6 тижнів, до трьох задач на день + «+N ще» (модалка), перемикач «Мої/Всі», навігація місяцями, кнопка «Сьогодні».
- Вкладка **«Завершені»** — для `ADMIN` там же чекбокси й масове видалення (`POST /tasks/bulk-delete`, зроблено 27.08.2026).

```
│         7             │ │       2       │ │        11         │ │   6 · 142 500 ₴  │
└───────────────────────┘ └───────────────┘ └───────────────────┘ └──────────────────┘
┌─ Воронка ────────────────────────────┐ ┌─ Потребує уваги ──────────────────────┐
│ Лід            ████████ 18           │ │ 🕐 Ліди без активності 7+ днів (5)    │
│ Переговори     ██████ 14             │ │ 📋 Ліди без задач (4)                 │
│ КП надіслано   █████ 11              │ │ 🔴 Прострочені задачі (2)             │
│ Договір на підп. ███ 6               │ │ 📉 КП без відповіді 5+ днів (3)       │
│ Договір підписано ████ 9             │ │ 📝 Договори без даних для тарифу (2)  │
└──────────────────────────────────────┘ └───────────────────────────────────────┘
┌─ Конверсія за джерелами (90 днів) ───────────────────────────────────────────────┐
│ Рекомендація   12 лідів → 5 договорів  42%                                       │
│ Сайт            9 лідів → 2 договори   22%                                       │
│ Реклама        14 лідів → 1 договір     7%                                       │
└──────────────────────────────────────────────────────────────────────────────────┘
```

Блок конверсии по источникам — главный отчёт менеджерской итерации: он отвечает на вопрос «куда вкладывать деньги на привлечение», ради которого лиды и заводятся в систему. Период по умолчанию — **90 дней**, и рядом с процентом всегда стоят абсолютные числа (FR-5.1.4): поток нерегулярный, а «50 %» из двух лидов — не показатель. Виджеты бухгалтерского контура (КЕП, обслуживание) появятся здесь только если система дойдёт до бухгалтеров — см. backlog в `01-functional-requirements.md`.

Правый блок — не «красивая аналитика», а рабочий список: каждая строка кликается в отфильтрованный список клиентов. Для `USER` — те же блоки, но только по своим клиентам, и без суммы договоров.

## Правила компоновки (чтобы экраны не расползлись)

| Правило | Значение |
|---|---|
| Шрифт | Inter (латиница + кириллица + украинские глифы), 14 px база, 13 px в таблицах |
| Сетка отступов | 8 px, только Mantine `spacing` (`xs/sm/md/lg`) |
| Радиусы | один на всё приложение: `defaultRadius: 'md'` |
| Акцентных кнопок | не более двух на экран; главное действие — всегда справа вверху |
| Цвет | один брендовый акцент (взять с сайта), остальное — нейтральная шкала |
| Статусы | фиксированная палитра, одна и та же в таблице, drawer, карточке и дашборде |
| Иконки | только `@tabler/icons-react`, 16/18 px |
| Модалки | максимум один уровень; вместо второй модалки — drawer или отдельный экран |
| Ширина | контент не ограничен, drawer 600 px, модалки `md` |

**Цвета статусов** задаются один раз в справочнике (FR-2.6) и берутся оттуда везде — не хардкодятся в компонентах.

## Обязательные состояния каждого экрана

Пропущенные состояния — самая частая причина ощущения «сырой самописной системы»:

1. **Загрузка** — `Skeleton` в форме будущего контента, не спиннер по центру.
2. **Пусто** — иконка + что это значит + кнопка действия («Клієнтів ще немає. Додайте першого або дочекайтеся заявки з сайту»). Про импорт из Excel не пишем — импорта нет (FR-2.15).
3. **Пусто после фильтра** — «Нічого не знайдено» + кнопка «Скинути фільтри» (это другое состояние, чем п. 2).
4. **Ошибка** — что случилось по-человечески + «Спробувати ще раз», без стек-трейсов. Мелким шрифтом внизу — **код запроса** («Код: `a3f9c1`», NFR-31.2) с копированием по клику: пользователь называет его в сообщении о проблеме, и разбор занимает минуту вместо часа.
5. **Нет прав** — «Недостатньо прав» вместо пустого экрана или редиректа в никуда.
6. **Обрыв сети** — тост «Немає зв'язку, повторюємо…», TanStack Query ретраит сам.

## Мобильная версия

Ровно то, что обещано в NFR-28: список «Мої задачі» и просмотр карточки клиента. Таблица превращается в карточки, drawer — в полноэкранный, фильтры — в bottom sheet. Канбана, редактирования карточки и контекстного меню по долгому нажатию на телефоне нет — FR-8.7 относится к планшетам и тач-десктопам.

**Два исключения из read-only** (решение от 26.08.2026): по задаче доступны **«Виконано»** (с обязательным полем результата для типов `ДЗВІНОК`/`КП`/`ДОГОВІР`, FR-3.5) и **«Перенести термін»** с теми же пресетами, что в ПКМ (сьогодні / завтра / +3 дні / тиждень). Причина простая: уведомления в Telegram ведут на задачу, менеджер открывает их в дороге — и полностью read-only экран означает, что напоминание он прочитал, а сделать с ним ничего не может. API уже есть, вёрстка — две кнопки; недели мобильной вёрстки это по-прежнему не стоит.

## Как проверить компоновку до того, как писать бизнес-логику

**День 3–4 первой недели: кликабельный прототип на настоящем Mantine** — реальные компоненты, фейковые данные, 4 экрана (список, drawer, карточка, задачи). Показать двум бухгалтерам, дать пощёлкать 15 минут.

Это лучше Figma по трём причинам: занимает день вместо недели, показывает реальное поведение таблицы и drawer, и превращается прямо в код приложения, а не выбрасывается. Правки компоновки после этого стоят часы; после написания всей логики — недели.
