# Технический план реализации

Документы 01–08 отвечают на «что делать» и «почему именно так». Этот отвечает на «в каком порядке и как понять, что этап закончен».

Что здесь есть и чего намеренно нет: нет повторения требований и обоснований — они в 01–08 и дублировать их значит завести второй источник правды, который разойдётся с первым. Есть только то, что при отсутствии придумывается на ходу и расходится: поверхность API, матрица прав таблицей, содержимое seed, критерии готовности этапов.

Оценка — **~6 недель** одним разработчиком: 4,5 на функциональность плюс 1,5 на тесты (раздел 5). Этапы и критерии готовности — раздел 4; это единственное место, где план работ описан, в остальных документах на него ссылка.

## 0. Критический путь: что проверить в первые два дня

Три вещи, которые при неудаче обесценивают всё остальное. Их надо проверить на настоящем сервере до того, как написана первая бизнес-логика.

**1. Поддомен и TLS подняты.** CRM живёт на `crm.wisexpert.com.ua` (решение от 26.08.2026, вариант Г). Нужны A-запись, `server`-блок в nginx и сертификат от certbot на новое имя. `BASE_PATH` остаётся `/`, префикс никуда не протягивается — это и есть главная выгода решения.

> **Проверка:** `https://crm.wisexpert.com.ua` открывается по HTTPS, **F5 на глубоком URL** (`/clients/<uuid>`) отдаёт приложение, а не 404; редирект с `wisexpert.com.ua/crm` работает; cookie после логина ставится host-only, без атрибута `Domain`.

**Порядок с сертификатом важен, если стоит Cloudflare:** certbot выпускается **до** включения оранжевого облака, либо через DNS-01. При включённом проксировании и «Always Use HTTPS» HTTP-01-челлендж уходит в редирект-петлю.

**2. nginx не уронил сайт.** CRM встраивается в конфиг работающего маркетингового сайта. Правило: `nginx -t`, затем `reload`, **никогда `restart`**. Перед правкой — копия конфига.

> **Проверка:** `wisexpert.com.ua` открывается до и после, `nginx -t` чист.

**3. Приём заявок с сайта.** После отмены импорта (FR-2.15) это единственный автоматический источник данных. Требует доступа к репозиторию сайта — единственная внешняя зависимость проекта.

> **Проверка:** реальная отправка формы создаёт лида в пуле «Нерозподілені» с задачей «Подзвонити за заявкою».

Порядок именно такой: сначала деплой пустого скелета, потом код. Обратный порядок — четыре недели работы и выяснение на пятой, что префикс не протянут.

## 2. Матрица прав

Прозой она уже описана (FR-0.1–0.3), но проверять e2e-тестами можно только таблицу. Источник правды — `packages/shared/permissions.ts`; фронт скрывает кнопки по ней же, но **это UX, а не защита**: guard стоит на каждом эндпоинте (NFR-17).

| Действие | `ADMIN` | `USER` |
|---|---|---|
| `client:read` — видеть любого клиента | ✅ | ✅ |
| `client:create` | ✅ | ✅ |
| `client:update` — поля, статус | ✅ | ✅ |
| `client:assign` — менять ответственных, брать себе | ✅ | ✅ |
| `client:delete` — мягкое удаление и восстановление | ✅ | ❌ |
| `task:create` / `task:assign` — любому | ✅ | ✅ |
| `task:complete` / `task:cancel` | ✅ | ✅ |
| `task:delete` | ✅ | автор своей |
| `comment:create` | ✅ | ✅ |
| `file:upload` | ✅ | ✅ |
| `file:delete` | ✅ | своя загрузка ≤ 24 ч |
| `user:manage` | ✅ | ❌ |
| `dictionary:manage` | ✅ | ❌ |
| `audit:read` | ✅ | ❌ |
| `export:run` | вся база | только свои клиенты и задачи |
| `web-leads:read` | ✅ | ❌ |

Пользователь с `isProtected` (FR-1.8) не деактивируется, не понижается в роли и не получает сброс пароля через интерфейс — только CLI, независимо от роли действующего.

**Что проверяется e2e обязательно** (NFR-37): `USER` не может удалить клиента, не может дёрнуть `/users`, не может прочитать `/audit`, не может скачать чужой файл по прямой ссылке, не видит `/web-leads`. Пять тестов, которые ловят самый дорогой класс ошибок.

## 3. Seed: что кладётся миграцией

Справочники, у которых нет CRUD-экрана (решение третьей волны), заводятся миграцией. Это не «тестовые данные» — это часть схемы, без них система не запускается.

**Статусы клиентов** (`ClientStatus`, FR-2.6) — порядок, `stage` и флаги критичны:

| `code` | `label` | `stage` | `sortOrder` | флаги |
|---|---|---|---|---|
| `NEW` | Лід | `LEAD` | 10 | `isDefaultForNew` |
| `IN_PROGRESS` | Переговори | `IN_WORK` | 20 | |
| `PROPOSAL_SENT` | КП надіслано | `IN_WORK` | 30 | |
| `CONTRACT_SENT` | Договір на підписанні | `IN_WORK` | 40 | |
| `WON` | Договір підписано | `WON` | 50 | `isTerminal` |
| `LOST` | Відмова | `LOST` | 60 | `isTerminal`, `requiresReason` |

Цвета берутся из палитры темы, а не выдумываются на месте: одна и та же в таблице, drawer, карточке и дашборде (`06-ui-layout.md`).

**Типы задач:** `ДЗВІНОК`, `КП`, `ДОГОВІР`, `ДОКУМЕНТИ`, `ЗУСТРІЧ`, `ІНШЕ`.

**Категории документов:** `КП`, `Договори`, `Установчі`, `Довіреності`, `Листування`, `Інше`.

**Источники лидов и причины отказа** — редактируемые справочники, но стартовый набор нужен, иначе первый лид будет не с чем связать. **Требуют реальных значений от заказчика** (`07-open-questions.md`, раздел 2); до ответа сидируется рабочая заглушка: источники — `Сайт` (обязателен, его проставляет FR-W5), `Рекомендація`, `Реклама`, `Холодний обдзвін`, `Інше`; причины — `Ціна`, `Пішов до конкурента`, `Закрив ФОП/бізнес`, `Не виходить на зв'язок`, `Інше`.

**`app_settings`:** `PROPOSAL_NO_REPLY_DAYS = 5` (FR-5.2), `LEAD_INACTIVE_DAYS = 7`, `FILE_MAX_MB = 25`.

**Чего в seed нет:** тестовых клиентов и задач. Демо-данные для локальной разработки — отдельный скрипт `pnpm seed:dev`, который на прод не попадает никогда.

## 4. Этапы и критерии готовности

Критерий — не «код написан», а проверяемое действие. Каждый этап заканчивается деплоем на прод.

> **История оценки.** Пересматривалась четырежды. Вверх — после детализации требований: реестр быстрых действий с ПКМ оказался отдельной работой на неделю. Вниз, до 6 недель, — решениями о границе системы: ушли импорт из Excel, группы клиентов, ZIP-экспорт, пост-договорные статусы с MRR и КЕП-контур. Ещё раз вниз, до 4,5, — вторым раундом сокращений: канбан, дедупликация файлов, сохранённые представления, CRUD-экраны пяти справочников, матрица уведомлений, тёмная тема, экран аудита. И обратно вверх, до 6, — включением тестов трёх уровней (раздел 5).

**Показывать менеджеру — основному пользователю первой итерации — после этапа 2.** Он найдёт половину недостающих полей раньше, чем будут дописаны задачи. Бухгалтеров подключать только когда система дойдёт до их контура (v1.1); в MVP их роль — сказать, каких данных им не хватает на карточке.

## 5. Тестирование

Тесты — часть работы над функцией, а не отдельный этап в конце. «Сначала сделаем, потом покроем» на проекте одного разработчика означает «не покроем»: к моменту, когда всё готово, писать тесты уже некому и незачем — оно же работает.

Три уровня, у каждого своя задача. Смысл в разделении: юнит ловит ошибку в правиле за миллисекунды, API ловит ошибку в контракте и правах, UI ловит то, что не видно ни там ни там — что кнопка не нажимается и экран не открывается.

| Уровень | Чем | Что ловит | Чего не ловит |
|---|---|---|---|
| **Юнит** | Vitest | Ошибку в бизнес-правиле: валидация реквизитов, нормализация телефона, календарь Kyiv, матрица прав | Всё, что связано с БД, HTTP и браузером |
| **API** | Vitest + `supertest` + настоящий Postgres | Права, контракт, валидацию, транзакционность, побочные эффекты (лента, аудит, уведомления) | Вёрстку, состояния экрана, работу мыши |
| **UI** | Playwright, headless Chromium | Что сценарий проходится целиком в браузере: клики, ПКМ, формы, тосты, переходы | Тонкую бизнес-логику — её дешевле проверить ниже |

Один раннер (Vitest) на юнит и API вместо связки Jest + Vitest: на фронте всё равно Vite, а два раннера с разными конфигами и разными способами мокать — лишний источник трения на проекте, где разработчик один.

### 5.1 Юнит-тесты: конкретные цели

Не «покрыть сервисы», а покрыть места, где ошибка тихая и дорогая:

- **Валидация украинских реквизитов** — ЄДРПОУ (8 цифр + контрольная сумма), РНОКПП (10 + контрольная), IBAN (`UA`, 29 символов, mod-97). Здесь много граничных случаев и готовые наборы валидных/невалидных значений; ошибка проявится на импорте чужих данных, а не на своих.
- **Нормализация телефона** (NFR-5.1) — `0671234567`, `+38 (067) 123-45-67`, `380671234567`, `067 123 45 67` дают один `+380671234567`; мусор даёт `null`, а не исключение. От этого зависят поиск (FR-2.10) и определение дублей (FR-2.2).
- **Календарь `Europe/Kyiv`** (FR-3.1.1) — задача без времени = `23:59:59` киевского дня; «прострочено» считается верно, когда UTC-контейнер уже в следующих сутках; переход на летнее время в последнее воскресенье марта и октября не сдвигает дедлайны. Это классическое место, где баг живёт полгода и выглядит как «система иногда путает даты».
- **Матрица прав** — `can(role, action, context)` прогоняется по всей таблице из раздела 2 как параметризованный тест. Одна таблица — один тест, зато любое изменение прав ловится сразу.
- **Маппинг веб-формы** (FR-W4) — известное значение, неизвестное значение (поле пустое + запись в ленту, заявка не падает), отсутствующее поле, генерация `displayName` вида `ФОП · +380637403599` и fallback на локальную часть email, когда телефона нет.
- **Правила задач** — результат обязателен при закрытии `ДЗВІНОК`/`КП`/`ДОГОВІР` (FR-3.5), причина обязательна при отмене любого типа.
- **Правила статусов** — выбор стартового статуса по `isDefaultForNew`, требование причины при `requiresReason`, отнесение статуса к `stage`.
- **Расписание дайджеста** (FR-4.5.2) — будни да, суббота и воскресенье нет, накопленное уходит в понедельник.

### 5.2 API-тесты: против настоящей БД

Мокать Prisma смысла нет — половина проверяемого поведения (транзакции, каскады, частичные уникальные индексы, `409` при конкурентной правке) живёт именно в базе. Поднимается отдельный `postgres_test`, миграции применяются перед прогоном, между тестами данные чистятся `TRUNCATE ... CASCADE`, справочники сидируются один раз.

Обязательный набор:

**Аутентификация и сессии**
- вход с верным и неверным паролем; блокировка email после 10 неудач на 15 минут (FR-1.5); лимит по IP не блокирует другого пользователя из того же офиса;
- ротация refresh-токена; смена пароля отзывает все сессии; сброс админом отзывает сессии и создаёт уведомление.

**Права** — тот самый набор, ради которого тесты и заводятся (NFR-37):
- `USER` получает `403` на `/users`, `/web-leads`, `DELETE /clients/:id`;
- `USER` экспортирует только своих клиентов, `ADMIN` — всю базу;
- запрос файла без авторизации — `403`, а не отдача файла;
- пользователь с `isProtected` не деактивируется и не понижается в роли через API (FR-1.8).

**Клиенты и воронка**
- создание лида четырьмя полями, статус проставился по `isDefaultForNew`;
- фильтры и форма ответа пагинации; `assigneeId=none` возвращает пул;
- поиск находит клиента по `0671234567`, если сохранён `+38 (067) 123-45-67`;
- `PATCH` с устаревшим `updatedAt` → `409` (NFR-46);
- смена статуса на `requiresReason` без причины → `400`; с причиной → запись в `client_status_history` **и** в `activity_events` в одной транзакции;
- `POST /clients/:id/claim` меняет `PRIMARY` и уведомляет прежнего ответственного;
- деактивация пользователя переносит его открытые задачи и клиентов на `ADMIN` одной транзакцией (FR-1.9).

**Задачи и файлы**
- закрытие звонка без результата → `400`;
- задача из пула создаётся с `assigneeId = null` и не роняет запросы списка;
- загрузка `.exe`, переименованного в `.pdf`, отклоняется по magic bytes (NFR-19);
- SVG отдаётся только как `attachment`, PDF и изображения — `inline` (FR-F11).

**Публичный эндпоинт заявок** (FR-W1–W6) — самая ценная группа, потому что это единственный вход данных извне:
- без токена ответ `200`, но клиент не создан;
- с токеном создаётся клиент в пуле, задача «Подзвонити за заявкою» без исполнителя и уведомления всем активным;
- повторная заявка с тем же телефоном не создаёт вторую карточку, а пишет событие в ленту;
- неизвестное значение `TaxSystem` не роняет заявку: поле пустое, запись в ленте, `WebLead.error` заполнен;
- тело больше 16 КБ и honeypot-поле отклоняются;
- payload с `test: true` сохраняется, но клиента не создаёт (FR-W8).

### 5.3 UI-тесты: восемь сценариев, не больше

Playwright, headless Chromium, против поднятого локально стека с тестовой БД. Восемь — это не «пока хватит», а сознательный потолок: UI-тесты самые медленные и самые хрупкие, и набор из полусотни начнёт падать по чужим причинам, после чего его отключат целиком. Лучше восемь, которые всегда зелёные и которым верят.

1. **Логін** — вхід, дашборд відкрився; невірний пароль не пускає.
2. **Заведение лида** — форма в четыре поля, клиент появился в списке и в «Мої».
3. **Заявка с сайта до взятия в работу** — заявка отправляется через API, лид виден в «Нерозподілені», «Взяти в роботу» назначает текущего пользователя, бейдж в сайдбаре уменьшился.
4. **ПКМ и оптимистичный откат** — правый клик по строке, «Змінити статус», тост «Готово», кнопка «Скасувати» в течение 5 секунд возвращает прежний статус (FR-8.8).
5. **Закрытие звонка требует результат** — чекбокс в списке задач открывает поле результата, пустое не принимается (FR-3.5).
6. **Чек-лист перед закрытием сделки** — перевод в «Договір підписано» показывает незаполненные поля блока «Для тарифу», «Пізніше» не блокирует переход (FR-2.0.5).
7. **Глубокий URL и обновление страницы** — F5 на `/clients/<uuid>` отдаёт приложение, а не 404. Дешёвый тест, ловящий целый класс проблем с деплоем.
8. **Права глазами `USER`** — у обычного пользователя нет пунктов «Користувачі» и «Довідники» в сайдбаре, прямой переход по URL даёт экран «Недостатньо прав», а не пустоту или редирект в никуда.

Отдельно проверяется то, что в требованиях названо главным (`06-ui-layout.md`): у каждого экрана есть все состояния — загрузка, пусто, пусто после фильтра, ошибка с кодом запроса, нет прав. Это не отдельные тесты, а проверка внутри сценариев выше.

### 5.4 Что не тестируем намеренно

- **Пиксельную вёрстку и visual regression** — Mantine отвечает за консистентность, а скриншотные тесты на проекте одного разработчика дают ложные падения чаще, чем находят проблемы.
- **Нагрузку** — пиковые 3 RPS и 10 пользователей (`02-non-functional-requirements.md`). Нагрузочный тест здесь измерял бы качество тестового стенда, а не системы.
- **Проценты покрытия как цель.** Цель сформулирована в NFR-37 и не меняется: CI ловит поломку прав доступа и бизнес-правил. Метрика покрытия при такой цели — способ написать много тестов на геттеры.
- **Чужой код** — Prisma, Mantine, Nest. Тестируется наша логика поверх них.

### 5.5 Инфраструктура и CI

Раскладка:

```
apps/api/src/**/*.spec.ts        # юнит: чистая логика, без БД
apps/api/test/**/*.api-spec.ts   # API: supertest + postgres_test
apps/web/src/**/*.spec.ts        # юнит фронта: хелперы, форматтеры
e2e/**/*.spec.ts                 # Playwright
```

Данные для тестов — **фабрики, а не дампы**: `makeClient({ status: 'PROPOSAL_SENT' })` создаёт валидный объект с осмысленными умолчаниями. Общий фикстурный дамп через месяц превращается в клубок, который никто не решается тронуть.

Гейты в CI (GitHub Actions, не на прод-сервере — на одном ядре VPS тесты гонять нечем):

| Событие | Что запускается |
|---|---|
| Pull request | lint, typecheck, юнит, API |
| Merge в `main` | всё выше + Playwright |
| Деплой | только с зелёного `main` (NFR-38) |

Прогон должен укладываться в **пять минут** на PR. Если API-тесты вырастут за этот бюджет — они гоняются параллельными шардами, а не сокращаются.

### 5.6 Цена в сроках

Тесты не бесплатны, и делать вид, что они впишутся в прежнюю оценку, — самообман:

| Работа | Когда | Дней |
|---|---|---|
| Инфраструктура: Vitest, supertest, `postgres_test`, Playwright, CI-матрица | этап 1 | 1 |
| Юнит-тесты бизнес-правил | по ходу этапов 2–4 | 1,5 |
| API-тесты | по ходу этапов 2–4 | 3 |
| Восемь сценариев Playwright | этапы 3–5 | 2 |
| **Итого** | | **~7,5 дней ≈ 1,5 недели** |

**Оценка проекта: ~4,5 недели → ~6 недель.** Это цена, за которую покупается конкретное: изменение прав доступа не проходит в прод молча, а рефакторинг перестаёт быть игрой в русскую рулетку. На системе, где хранится клиентская база бухгалтерской фирмы, размен правильный.

Порядок написания внутри этапа: сначала API-тест на права (он же спецификация эндпоинта), потом реализация, потом юнит на правила, которые всплыли по дороге. Playwright-сценарий добавляется, когда экран стабилизировался, — не раньше, иначе переписывается трижды.

## 6. Определение готовности задачи

Применяется к каждой задаче, а не только к этапу:

- типы API — из общего пакета, руками на фронте не переписываются;
- guard и проверка владения объектом на эндпоинте, не только в UI;
- DTO через `class-validator` с `whitelist: true, forbidNonWhitelisted: true`;
- тексты интерфейса — украинские, ошибки под полем человеческим языком;
- у экрана есть все состояния: загрузка, пусто, пусто после фильтра, ошибка, нет прав;
- мутация возвращает полный обновлённый объект;
- **есть тесты уровня, соответствующего задаче** (раздел 5): бизнес-правило — юнит; эндпоинт — API-тест, и в первую очередь на права; законченный пользовательский сценарий — Playwright, когда экран стабилизировался.

## 8. Чего в плане нет намеренно

**Оценок в часах по каждой задаче.** На проекте одного разработчика они превращаются в самообман: недельные этапы с проверяемым критерием готовности дают ту же управляемость без ритуала.

**Отдельного staging-окружения.** Каждый этап заканчивается деплоем на прод, система в это время ещё никем не используется. Staging появится, когда в CRM будут живые данные — тогда же и понадобится (`04-deployment.md`).

**Плана миграции данных.** Импорта нет (FR-2.15), система стартует пустой.
