# Беклог майбутніх фіч

Сюди записуються ідеї та побажання, які виникають по ходу роботи з системою,
але свідомо не робляться зараз — щоб не губилися і не переказувались по пам'яті.
Це не план (`09-implementation-plan.md`) і не гэп-аналіз вимог
(`08-gap-analysis.md`): там — що і чому вирішено для MVP, тут — що назбиралось
понад це під час реальної роботи.

Формат запису: дата, короткий опис, чому не зараз. **Статус: ⬜ не почато ·
🟡 в роботі · 🟢 зроблено.** Пункт переїжджає в `09-implementation-plan.md`
(або в окремий етап), коли до нього доходить черга — тут він лишається
закресленим для історії, а не видаляється.

## Записано 27.08.2026

### ⬜ Календар задач — глобальний огляд

Окремий екран (або вкладка на «Задачах»): календарна сітка місяць/тиждень,
у кожному дні — кількість і перелік задач з терміном на цей день. Зараз
задачі бачаться лише списком, згрупованим за «Прострочені / Сьогодні / Цього
тижня / Пізніше» (`features/tasks/group.ts`) — це добре для «що робити
просто зараз», але не дає відповіді на «що заплановано на 15-те число».

Дані вже є (`GET /tasks?dueBefore=...`), нового бекенду, скоріш за все, не
знадобиться — лише інша візуалізація існуючого списку по місяцю.

### 🟢 Деталізація стрічки активності — зроблено 27.08.2026

Рядки стрічки (`features/activity/ActivityFeed.tsx`, винесено з
`ClientCardPage.tsx`) тепер розгортаються по кліку на шеврон — показують те,
що зберігає `ActivityEvent.payload`.

З'ясувалось при реалізації, що для найціннішого випадку — `field_changed` —
payload насправді **не** зберігав значення, лише перелік імен змінених
полів (`{ changed: string[] }`); те саме для `task_updated`/`task_reassigned`.
Довелось спершу дописати бекенд: новий `diffChanged()` в `activity.service.ts`
порівнює «до» і «після» та пише `{ changed: [{ field, from, to }] }` —
використано в `clients.service.ts` (`update`, `updateContact`) і
`tasks.service.ts` (`update`). Заразом виявився і виправлений побічний баг:
DTO-класи (target ES2022+, `useDefineForClassFields`) мають усі оголошені
поля власними властивостями зі значенням `undefined` навіть коли клієнт їх
не надсилав — `Object.keys(dto)` тому завжди містив зайві поля; тепер
`diffChanged` їх відфільтровує.

`status_changed` довантажено мітками статусу/причини й коментарем прямо в
payload (щоб фронт не лазив у довідники по id), `contact_added`/
`contact_removed`/`field_changed` (contact) — іменем контактної особи.
Фронт (`ActivityDetails.tsx`, `labels.ts`) показує diff-таблицю з людськими
назвами полів для `field_changed`, текст результату для
`contact_logged`/`task_completed`, причину для `task_cancelled`, мітки й
коментар для `status_changed`, дати для `task_snoozed`, назву файлу/тегу/
контакту де є.

### ⬜ Коментарі — інтерфейсу немає взагалі

Виявлено як супутнє до пункту вище: `POST /comments` і розбір @згадок
(FR-2.17) готові на бекенді, але в жодному екрані немає ні поля для
додавання коментаря, ні списку існуючих. Стрічка активності показує тип
`comment`, але сам текст ніде не прочитати. Потрібно на картці клієнта і на
картці задачі (`TaskCardPage.tsx`, з'явилась 27.08.2026) — панель коментарів
за зразком `FilesPanel`.

### ⬜ Повна форма створення задачі з прив'язкою клієнта одразу

27.08.2026 задачі отримали картку (`TaskCardPage`, `/tasks/$taskId`) з
можливістю прилінкувати клієнта заднім числом — це закриває нагальну потребу
дешево, без нової форми. Але для випадку «одразу знаю, для якого клієнта і
з яким типом задача» зручніше було б одне модальне вікно на кшталт «Новий
лід» на екрані клієнтів: заголовок + клієнт + тип + виконавець + термін за
один крок, без переходу «створив → відкрив → відредагував».

### ⬜ Статуси клієнтів — редаговані через довідники

Зараз `ClientStatus` заводиться лише міграцією (розділ 3 плану, свідоме
рішення: порядок, `stage` і флаги `isDefaultForNew`/`isTerminal`/
`requiresReason` критичні для логіки воронки, тому змінювати їх з UI
небезпечно без додаткових перевірок). Побажання — щоб статуси лідів
з'явились у «Довідниках» поруч із джерелами/причинами/тегами
(`DictionariesPage.tsx`), з можливістю редагувати назву й порядок так само,
як зараз для трьох існуючих редагованих довідників.

Зробити технічно нескладно (`DictionariesService`/`UpsertDictionaryEntryDto`
вже підтримують довільний код+назва+sortOrder), але для статусів знадобиться
окремо продумати, які поля можна чіпати з UI, а які — ні (`stage`,
`isDefaultForNew`, `isTerminal`, `requiresReason` міняти небезпечно), і чи
можна взагалі видаляти/додавати статус, а не лише перейменовувати — це вже
зачіпає воронку і звітність на дашборді.

### ⬜ Масове видалення завершених задач (ADMIN)

На вкладці «Завершені» (`TasksPage.tsx`, з'явилась 27.08.2026) — вибір
кількох задач і видалення одним разом, за зразком масових дій на екрані
клієнтів (`FR-2.13`/`FR-8.3`, `BulkToolbar` у `ClientsPage.tsx`). Бекенд поки
вміє лише `DELETE /tasks/:id` по одній (автор або `ADMIN`) — знадобиться або
цикл запитів з фронту (як у завантаженні файлів), або новий bulk-ендпоінт.

### ⬜ Редагування контактної особи на картці клієнта

Знайдено 27.08.2026 на реальному ліді з сайту: заявка прийшла з іменем, а
контактна особа створилась з порожнім `fullName` (веб-форма пише ім'я тільки
в `Client.displayName`, не в `Contact.fullName`) — і виправити це вручну не
можна: `ContactsPanel` на фронті вміє лише переглядати і додавати нову особу,
ні редагування, ні видалення немає. Бекенд уже готовий (`PATCH`/`DELETE
/clients/:id/contacts/:contactId`, є і в контролері, і в сервісі, FR-2.2.х).

Побажання щодо реалізації — модалка (той самий `ContactDto`-набір полів, що
й у формі додавання: ПІБ, посада, телефон, email, ознака основного
контакту), а не інлайн-форма на картці контакту.

### 🟢 Хлібні крихти — зроблено 27.08.2026

Додано `Breadcrumbs` на картки клієнта і задачі («Клієнти / {назва}»,
«Задачі / {заголовок}») — раніше не було зрозуміло, в якому розділі
